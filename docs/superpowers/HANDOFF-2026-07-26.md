## 4. THE BLOCKER — the handoff's ramp values are wrong

Task 3 implemented `luminance.ts` exactly as the plan specified, and **three assertions fail**. The subagent correctly refused to loosen them. These are real defects in the design handoff's own numbers, not implementation mistakes. Two independent derivations (the subagent's, and a hand-check) agree.

### Defect A — the 4.5:1 contrast claim is false

The handoff states: *"With the flip, everything clears 4.5:1."* It does not.

`foregroundFor` picks `#06120c` when background luminance > 0.30, else `#ffffff`. The actual WCAG crossovers:

| Ink | Clears 4.5:1 when background luminance is |
|---|---|
| `#ffffff` (L = 1.0) | **≤ 0.1833** |
| `#06120c` (L ≈ 0.00498) | **≥ 0.1974** |
| `#000000` (L = 0) | ≥ 0.175 |

Two problems follow:

1. **The 0.30 threshold is in the wrong place.** Every background with luminance between 0.1833 and 0.30 gets white ink and fails. Eight sampled points fail — four on each ramp, all on the *gain* side:

   | Ramp | t | bg RGB | bg L | measured ratio |
   |---|---|---|---|---|
   | NORMAL | 0.25 | 62,137,103 | 0.1989 | 4.218 |
   | NORMAL | 0.30 | 56,146,106 | 0.2244 | 3.827 |
   | NORMAL | 0.35 | 61,154,112 | 0.2527 | 3.468 |
   | NORMAL | 0.40 | 66,163,117 | 0.2864 | 3.122 |
   | CVD | 0.35 | 56,132,182 | 0.2072 | 4.082 |
   | CVD | 0.40 | 62,139,189 | 0.2316 | 3.728 |
   | CVD | 0.45 | 68,147,195 | 0.2604 | 3.383 |
   | CVD | 0.50 | 74,155,201 | 0.2912 | 3.077 |

2. **`#06120c` leaves a dead band.** Even with a perfectly placed threshold, backgrounds in **0.1833 – 0.1974** clear 4.5:1 against *neither* ink. `#000000` does not have this problem (its ≥ 0.175 requirement overlaps white's ≤ 0.1833), so switching the dark ink to pure black removes the dead band entirely.

**Recommended fix (needs user sign-off, since it deviates from the handoff):** change the dark ink from `#06120c` to `#000000` and move the threshold from `0.30` to `0.1833`. Then verify by computation that no interpolated point on either ramp fails — do not assume.

### Defect B — `RAMP_CVD` is not luminance-monotonic

The handoff calls RAMP_CVD *"same luminance profile"* as RAMP_NORMAL. It isn't. Between the `t = -0.3` stop `[146,88,32]` and the `t = -0.1` stop `[106,84,70]`, luminance **falls** as t rises:

```
t=-0.30  L=0.131947
t=-0.25  L=0.122178   ↓
t=-0.20  L=0.113302   ↓
t=-0.15  L=0.105469   ↓
t=-0.10  L=0.098470   ↓
```

Cause: R drops 146→106 while B rises 32→70, and blue's 0.0722 luminance weight cannot offset red's 0.2126. `RAMP_NORMAL` passes monotonicity cleanly; only CVD is broken.

This matters because luminance-monotonicity is the *entire point* of the redesign's colour work — it is what makes magnitude survive greyscale and colour-vision deficiency. Shipping CVD as-is would mean the colourblind ramp is the one that fails colourblind users.

**Fix:** re-pick the CVD stops between −1.0 and 0 so luminance rises monotonically while keeping the orange-loss identity. Likely just needs the `-0.3` and `-0.1` stops darkened/rebalanced. **Compute, don't eyeball** — write a script, sample at 0.01, assert strictly increasing.

### A verification script was being written when the session ended

It was going into scratch (now gone). Rewrite it — roughly: implement `ch/L/lerp/ramp` in plain node, print stop luminances, sample both ramps at 0.01 and report every non-increasing step, and print the three crossover thresholds. That script is how both defects should be *confirmed fixed*, not by trusting a test that only samples every 0.05.

### Also worth deciding

The 4.5:1 bar may be stricter than needed for the large tickers (22px @ 700 weight is WCAG "large text" → 3:1). But small tiles render at 11px, which does need 4.5:1. Recommend keeping 4.5:1 everywhere rather than making the threshold size-dependent — simpler, and the handoff asks for it.
